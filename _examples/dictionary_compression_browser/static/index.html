What you are looking at

The dictionary row starts level with the others and drops after a few seconds. That is deliberate: the dictionary costs its own size in bytes, so the server withholds it until a connection has carried enough traffic to earn it back. Before that point the connection uses the built-in dictionary, which both sides compile in and which costs nothing to deliver, which is why the whole-session bytes / message stays above the steady-state ratio shown in the card.

permessage-deflate runs here at CompressionLevel: 6. The default is 0, which is flate.NoCompression — the connection negotiates the extension and then stores instead of compressing, measuring slightly worse than no compression. It is an easy default to leave in place, and it makes any comparison meaningless.

Wire bytes are measured on the server, at the socket, after compression. They have to be: a browser cannot see permessage-deflate at all, because the WebSocket API inflates those frames before JavaScript gets them. Counting in the page would report deflate as saving exactly nothing, which would be an artefact of the measurement rather than a result. Counts are per mode across all tabs, so bytes ÷ messages stays right however many you open.

Server cache hits need real fan-out to show — measured 0% at 3 subscribers, 68% at 30, 99% at 2000. A few browser tabs will sit near zero, and that is fine: with three subscribers there is almost nothing to share.
